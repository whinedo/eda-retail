# E23 business duplicates

Objective: make business duplicates (resent notices, replans that re-request served steps, a shared order) produce no repeated effects, and measure it with experiment E23. Branch `feat/e23-business-uniqueness` from main 3eb2aa7; delivery `single-pr` (one PR per experiment, user rule).
Test runners: `uv run pytest -q --ignore=tests/integration -m "not integration and not slow"` (unit); integration and experiments only in CI.

## Specs

- S1 "Reembolso único por (incidencia, pedido): lookup en src/eda_retail/executor_issue_refund/handler.py:38 + migración 0025 con índice único, que se detiene sin borrar si hay duplicados (patrón de la 0023)."
  - The `issue_refund` executor returns the refund already registered for the step OR for the same (incident, order), even under another `step_id` / `idempotency_key`. Unique index `executor_issue_refund.refunds_incident_order_key (incident_id, order_id)` in migration 0025 (revises 0024); the per-step index from 0023 stays.
- S2 "Aviso único por (incidencia, pedido, versión del plan): src/eda_retail/executor_notify_customer/handler.py:64."
  - `customer_messages` gets a `plan_version` column (migration 0025, nullable for rows written before it) filled from `ExecuteStep.plan_version` (the incident's plan version when the saga requests the step, orchestrator/saga.py:167). The executor returns the existing message for the same step (as today) OR for the same (incident, order, plan_version). Unique index `executor_notify_customer.customer_messages_incident_order_version_key (incident_id, order_id, plan_version)`.
  - Migration 0025 stops with an error and deletes nothing when `refunds` already has repeated (incident_id, order_id) pairs (0023 pattern). The new column has no data yet, so the notice index cannot find duplicates.
  - The harness E21 control (`BUSINESS_UNIQUES`) also drops the two new indexes.
- S3 "Precisar specs/idempotency." Requirements «Un aviso por cliente y pedido» (one notice per incident, order and plan version) and «Reservas, reenvíos y reembolsos sin duplicar» (one refund per incident and order, not per step) state the rules of S1–S2, with scenarios that have a test each.
- S4 "Oráculo de replan propio para las variantes (b) y (c), y dataset con un pedido compartido para (d). Ojo: el oráculo indexa por pedido."
  - (b) a replanner that, besides the base oracle plan, asks again for the completed `file_claim` and `notify_customer` of the order under new `step_id`s.
  - (c) a replanner that, after a refund, proposes `issue_refund` again under a new `step_id` in a later revision (the first revision adds the refund and a new `reserve_stock` that can fail again, so a later revision exists).
  - (d) a dataset where part of the orders get a second notice with a different `carrier_notice_id` and the same labels, so the per-order oracle answers both incidents the same way.
- S5 E23 as specified in specs/experiments/spec.md («E23 Duplicados de negocio…», H23): 50 incidents, 50 % `reserve_stock` failures, variants (a)–(d); per-variant report: `incident_id` per `carrier_notice_id`, discards with reason `duplicate_notice`, claims per (incident, order), notices per (order, plan version), refunds per incident and order, active reservations per order (per (incident, order) in (d)); H23 holds when every count is at the maximum set by `idempotency` and `incident-interpretation`, plus invariants I1–I5 (gate I1, I2). The injections (notice resends in order and concurrently) go to specs/synthetic-data with the experiment. One test per scenario.
- S6 "Es Risk item 1: requiere un verificador independiente."
