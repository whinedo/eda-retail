# Async command handlers (202 at once, work in background)

Objective: commands answer 202/422 at once; long work (LLM, external services) runs in a per-component job worker and its result is an event. Fixes the E6 escalations of the events version.
Branch: `feat/eda-async-commands` (from `feat/eda-components`, includes `feat/e6-escalation-reasons`). Delivery: ask-on-risk. Test runner: pytest (unit locally with closed ports; integration only in CI), vitest untouched.

## Specs

- S1 (L1, L3) Commands whose work is long return 202 or 422 at once and do the work in background, emitting the result event at the end: "creía que habíamos acordado que los comandos devolvían 202 al momento y luego ejecutaban en "segundo" plano, emitiendo el evento del cambio de estado (si lo hay) al final, es decir, el comportamiento correcto de un Aggregate de DDD". Applies to `CreatePlan` (planner), `RevisePlan` (replanner) and `ExecuteStep` of the four step executors: "sí, hazlo así con ExecuteStep incluido". Acceptance checks that need no LLM or external service (payload schema, `plan_exists`, `revision_exists`, `action_not_handled`, `incident_mismatch`, `missing_context`) still answer 422 in the request. The 202 is durable: the job is stored in the same transaction as the inbox row, so a crash after the 202 does not lose the work; a repeated `command_id` replays the stored response without a second job. Assumption: `inventory` `ExecuteStep` (`reserve_stock`, `release_stock`) stays synchronous because it does no external I/O (the Aggregate decides inside its transaction); reported to the user.
- S2 (L4) A job left pending or half done by a crash is taken again when the worker restarts; its result (events, state) is written once. A late rejection inside the job (a race the acceptance check could not see) writes no events and is logged; the saga deadline handles it.
- S3 (L4) Saga deadlines measure the target system, not our queue: a deadline starts when the dispatcher first sends the command (whether or not the target answers), not when the saga enqueues it. "Paso sin respuesta" (executor down) still times out.
- S4 (L4) A second `StepFailed` in the same plan version while a `RevisePlan` for that version is pending does not enqueue another `RevisePlan` and does not escalate with `command_rejected`; the pending revision continues. If the revised plan keeps a step that failed meanwhile, the saga handles that failure on the new version with the normal rules.
- S5 (L2) The E6 report counts escalations by reason in both versions (commit f7a44ec).
- S6 (L4) The experiments harness runs each LLM-bound or long unit (job workers, interpreter consumer) on its own thread, as separate processes would, so E6 measures the design and not a single-threaded harness.
- S7 design.md §4.2/§4.4 and the event-backbone, incident-planning and step-execution specs say S1–S4; the stale sentence "Si el handler llama al LLM, lo hace antes de su transacción" is removed (spec/design were wrong; corrected in the same change and reported).
